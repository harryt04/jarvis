## Purpose and current state

RepoStaff proposes AI staff for existing GitHub software teams: ephemeral implementation agents, a persistent staff-engineer agent named Marshall, and a management dashboard, supported by a customer-owned knowledge repository. The initial audience of 5–30 engineers is a hypothesis. The proposed workflow ends at merge; autonomous production deployment, production credentials, regulated-enterprise features and custom workflow stages are outside the described MVP. The repository is a company knowledge base plus an implemented public marketing application, **not an implemented agent platform**. `apps/management`, orchestration, PostgreSQL persistence, integration consumers and worker/Marshall runtimes do not exist in the inspected tree. **Request to container, implemented but unproven on Cloudflare.** The edge Worker redirects `www` to apex, obtains a Durable Object named from `IMAGE_ID`, proxies the request and adds staging noindex headers. Failure returns 503 with retry/no-store headers; restart resets readiness. The config generator requires a digest-pinned Cloudflare registry reference, derives a short image ID and generates separate staging/production host configuration. This is public marketing lifecycle glue, not product orchestration or tenant isolation. ## Planned platform boundaries

The approved direction separates public marketing, authenticated management, portable orchestration and hostile task execution. PostgreSQL owns application state and authoritative budget admission; a GitHub brain owns durable knowledge/policy. PlanetScale through Cloudflare provisioning/billing is selected for hosted PostgreSQL, without a chosen ORM or proven connection. Agents receive pinned, read-only brain snapshots; changes to policy become commits. Fresh VMs are required even on customer hardware; Docker alone is not the security boundary. BYOK Anthropic/OpenAI and brokered scoped capabilities are intended; subscription logins are excluded. All platform authorization, isolation, credential custody, budget fencing, cleanup and recovery controls remain plans. [Architecture, lines 7–39](https://github.com/harryt04/repo-staff/blob/4b45bf87ceb745d39f0dd9395e3e211764aead10/docs/product/architecture-outline.md#L7-L39); [security status and lifecycle](https://github.com/harryt04/repo-staff/blob/4b45bf87ceb745d39f0dd9395e3e211764aead10/docs/product/security-and-trust.md#L3-L64).

Provider boundaries require inward-facing adapters, domain-owned authorization/spend, atomic PostgreSQL reservations, idempotent side effects and stale-lease fencing. Provider meters are reconciliation evidence, not balances. Customer-owned brain portability is narrower than exporting application history, credentials and live services. Full control-plane self-host setup/support is demand-led post-MVP; customer-run compute is a separate option. Billing/MoR, secret/blob vendors, retention, orchestration placement and several operational contracts remain open. [Provider contract](https://github.com/harryt04/repo-staff/blob/4b45bf87ceb745d39f0dd9395e3e211764aead10/docs/product/provider-boundaries.md#L7-L55).
