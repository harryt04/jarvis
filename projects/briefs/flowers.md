## Purpose and product boundary

This is the public marketing and inquiry site for Elisabeth’s Utah mobile flower bar: visitors build bouquets, choose kindness cards, discover events, join an email list, or request an event. It captures leads rather than confirming availability, accepting payment, or creating reservations. The terms explicitly make inquiries nonbinding until availability and terms are confirmed separately ([app/terms/page.tsx:60–71](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/app/terms/page.tsx#L60-L71)). Corporate recurring deliveries are advertised, but no subscription billing or fulfillment system appears in the application.

`company-brand.md` is the project’s stated brand authority: Sunshine Flower Bar replaces retired “Just Because Flowers”; “just because” remains the tagline. Voice should sound warm, personal, lightly funny, and rooted in kindness. Photography, generous space, semantic yellow/cream/olive tokens, Playfair Display/Nunito with sparse Dancing Script/Pacifico, and automatic device dark mode are deliberate project constraints, not general preferences to extrapolate to Harry’s other projects ([company-brand.md:3–15, 41–102](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/company-brand.md#L3-L102)).

## Architecture and visitor paths

Next.js App Router owns the public page and two POST handlers. `app/page.tsx` composes thirteen section components; the root layout supplies shared navigation/footer, Google fonts, Vercel Analytics, and Speed Insights. Navigation uses `/#section` links, including from the implemented `/privacy` and `/terms` pages ([app/page.tsx:1–33](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/app/page.tsx#L1-L33), [app/layout.tsx:69–84](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/app/layout.tsx#L69-L84), [components/Header.tsx:6–13](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/components/Header.tsx#L6-L13)). Content is maintained in source, including one yearless August 26 pop-up and three bouquet tiers; no CMS/calendar integration establishes current availability ([PopUpsSection.tsx:1–8](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/components/Sections/PopUpsSection.tsx#L1-L8), [PricingSection.tsx:3–26](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/components/Sections/PricingSection.tsx#L3-L26)).

**Email signup:** `SunshineClubSection` embeds `EmailSubscribeForm`. React Hook Form uses the shared Zod email schema, sends JSON to `/api/subscribe`, checks both HTTP status and `success`, then resets and displays the returned message. The route validates again, inserts `{email, submittedAt}`, returns 400 for schema failures, 502 for database failures, or 200 on insertion. Mongo error code 11000 also returns successful “already on” acknowledgement. No index creation, normalization, or uniqueness provisioning was found, so duplicate prevention depends on external database configuration; this branch is not evidence that duplicate emails are actually prevented ([EmailSubscribeForm.tsx:24–57](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/components/EmailSubscribeForm.tsx#L24-L57), [subscribe/route.ts:6–65](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/app/api/subscribe/route.ts#L6-L65)). Signup only saves an address; it does not send confirmation or register a Resend marketing contact.

**Booking inquiry:** `ContactForm` uses `contactSchema`, an alias of `bookingSchema`; the API imports `bookingSchema` directly. Name and valid email are required. Both consent properties must be booleans, but may be false; phone, date, location, guest estimate, and message are optional strings, with only message capped at 1,500 characters. There is no phone/date/guest-count format validation or name trimming. The form defaults both consents false. POST `/api/contact` validates, inserts all parsed fields plus `submittedAt`, then awaits email followed by Discord. Database failure returns 502 and skips notifications; malformed JSON reaches the outer 500 handler. Success means the request was saved and notification helpers returned, not that a booking or customer follow-up occurred ([lib/validation.ts:3–26](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/lib/validation.ts#L3-L26), [contact/route.ts:8–59](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/app/api/contact/route.ts#L8-L59)).

The contact UI checks HTTP status, resets on success, and uses a special “we’ll email you/check spam” message when phone is blank. Neither form catches rejected fetches or JSON decoding failures, so those failures bypass their explicit feedback state. There is no offline queue, idempotency key, submission identifier, or reconciliation UI; retrying an uncertain contact submission can create another record ([ContactForm.tsx:26–70](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/components/ContactForm.tsx#L26-L70)).

## Storage, integrations, and trust boundaries

`lib/mongo-client.ts` centralizes the actual names: database **`sunshineflowerbar-${NODE_ENV}`**, collections **`bookingRequests`** and **`emailSubscribers`**. It requires `MONGODB_URI`, caches one connection promise globally, and sets pool size 10. A rejected cached promise is not cleared for a subsequent reconnect. Database selection does not use the URI’s default database; preview/production separation relies on the environment/URI configuration, not a Vercel deployment identifier ([lib/mongo-client.ts:3–37](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/lib/mongo-client.ts#L3-L37)).

Email requires `RESEND_API_KEY` and `CONTACT_NOTIFICATION_EMAIL`; missing configuration warns and returns. `RESEND_FROM_EMAIL` defaults only when nullish, so a copied empty value does not select the documented fallback. Customer fields are HTML-escaped, the customer email becomes `replyTo`, and the message goes to the operator, not the customer. Thrown send errors are swallowed and the result is ignored ([lib/email.ts:5–68](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/lib/email.ts#L5-L68)). Supplemental local dependency inspection of installed Resend 6.17.1 (`node_modules/resend/dist/index.mjs:851–858,1160–1213`, matching [package-lock.json:9078–9080](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/package-lock.json#L9078-L9080)) confirms provider/network failures can resolve as `{data:null,error}`; those failures need not even reach the helper’s error log.

Discord is similarly optional via server-only `DISCORD_CONTACT_WEBHOOK_URL`. It posts the complete inquiry and consent flags with `?wait=true`, allows mentions of two fixed operators, logs non-OK responses/network exceptions, and returns without propagating failure. Neither integration persists delivery IDs/status, retries, uses an outbox, or sets an explicit timeout; sequential waits delay the API acknowledgement ([lib/discord.ts:3–55](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/lib/discord.ts#L3-L55)).

These are unauthenticated public write endpoints; inspected handlers have no rate limit, CAPTCHA, or authorization gate. MongoDB credentials and notification secrets remain server-side. The Discord body combines unescaped customer text with instructions to “Lily”; any external automation must treat that text as untrusted. Crucially, the instruction prefers texting whenever a phone exists, while the privacy page promises texts only with consent. No SMS sender is implemented here, so actual follow-up behavior is unknown, but this instruction/policy conflict needs review before automating it ([lib/discord.ts:18–30](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/lib/discord.ts#L18-L30), [privacy/page.tsx:75–95](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/app/privacy/page.tsx#L75-L95)).

## Verification, decisions, and durable gotchas

GitHub Actions targets pushes/PRs to `master`, installs Node 24, runs `npm ci`, then `npm run ci`. The script is **`prettier --write .; npm run build; npm run test`**: it mutates files, continues after formatting/build failures because of semicolons, and its final status can reflect only tests. It never invokes `npm run lint`, despite AGENTS calling it lint/validation. Separate real commands are `npm run lint`, `npm run test`, `npm run build`, and documented `npx tsc --noEmit`; none were executed here ([package.json:5–12](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/package.json#L5-L12), [ci.yml:3–22](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/.github/workflows/ci.yml#L3-L22), [AGENTS.md:3–27](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/AGENTS.md#L3-L27)). Tests cover schemas in Node, not routes, notification outcomes, or UI. Several negative name/email cases also omit required consent booleans, weakening isolation of their claimed checks ([tests/validation.test.ts:43–70](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/tests/validation.test.ts#L43-L70)).

Harry’s latest commit explicitly made SMS opt-in optional even with phone supplied, superseding the earlier required-consent rule; retain that decision unless intentionally revisited ([commit 2eed694](https://github.com/harryt04/flowers/commit/2eed694c26f251e36c92578036d9377424d6af9b)). Other drift: README still names `corporate_leads` and obsolete `inquiryType`; AGENTS mentions absent `.agents/specs/` and tentatively missing legal pages that now exist. Brand policy forbids decorative gradients/icon grids, yet the hero gradient and illustrated step grid remain implemented ([README.md:48–56](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/README.md#L48-L56), [HeroSection.tsx:8](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/components/Sections/HeroSection.tsx#L8), [HowItWorksSection.tsx:28–47](https://github.com/harryt04/flowers/blob/2eed694c26f251e36c92578036d9377424d6af9b/components/Sections/HowItWorksSection.tsx#L28-L47)).
