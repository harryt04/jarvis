## Purpose and current state

Platter serves home cooks and informal groups who choose recipes, specify people fed, review ingredients against what they already have, and shop from a shared list. Its durable unit of collaboration is a list with one active shopping run, not a calendar or persistent household pantry. Meal scheduling, leftovers, inventory depletion, retailer checkout, and retained purchase ledgers are explicit non-goals ([PRD:48–61](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/docs/mvp/prd.md#L48-L61)). “Household” should therefore be read as a use case, not a separate authorization tenant.

The repository has substantive implementation beyond its foundation. Recipe versioning, selection, grocery derivation, Purchased actions, run completion, Dexie replay, and Socket.IO invalidation have actual code. Conversely, the scaffold document still says feature lanes are deferred, and the backlog describes an initial implementation frontier. These are planning artifacts, not reliable completion reports. AGENTS describes incremental implemented slices and remaining offline/collaboration work; the architecture is a better current navigation map ([AGENTS:1–24](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/AGENTS.md#L1-L24); [backlog:1–19](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/docs/mvp/backlog.md#L1-L19); [architecture:3–7](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/docs/mvp/architecture.md#L3-L7)). Neither source presence nor acceptance-test listings establishes that the full PRD is demonstrable.

## Recipe input to deterministic shopping requirements

The manual editor persists through recipe POST/PATCH, including typical people fed and structured ingredient fields. Editing creates versioned facts; the UI explicitly explains that existing selections remain pinned until a member accepts a newer version ([draft editor:258–289](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/components/recipes/draft-editor.tsx#L258-L289), [1113–1116](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/components/recipes/draft-editor.tsx#L1113-L1116); [recipe route:175–238](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/app/api/v1/recipes/[recipeId]/route.ts#L175-L238)). Drafts and usable recipes are distinct; incomplete content is not automatically selectable.

The ingredient parser handles fractions, ranges, identity normalization, confidence, and compatible conversion rather than outsourcing arithmetic to an AI service ([ingredient parser:144–242](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/lib/recipes/ingredient-parser.ts#L144-L242), [353–459](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/lib/recipes/ingredient-parser.ts#L353-L459)). Structured editor corrections override stale original prose during grocery derivation. The original line remains provenance; malformed scale data yields a readable ingredient with no fabricated quantity ([groceries:164–219](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/lib/recipes/groceries.ts#L164-L219)). Decimal arithmetic uses 40-digit precision, scales both range endpoints, and separates source quantity, precise requirement, and countable whole-unit suggestions ([scaling:10–95](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/lib/recipes/scaling.ts#L10-L95)).

Adding a recipe authenticates, validates the request, checks active list membership and run identity, verifies recipe accessibility through owner/list-share/public filters, and loads the usable immutable version. It checks operation receipts before optional base-revision conflicts. The selection is saved with a revision compare-and-swap, increment, and receipt; a content-free realtime event follows as best effort ([selection route:138–255](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/app/api/v1/lists/[listId]/selections/route.ts#L138-L255), [271–325](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/app/api/v1/lists/[listId]/selections/route.ts#L271-L325)). The people ratio belongs to the selection, not the recipe.

Grocery generation derives items from pinned selection/version pairs plus manual additions. High-confidence normalized identity and compatible dimensions permit merging; unknown quantities and uncertain matches remain conservative. Each contribution retains selection, recipe, version, title, and ingredient provenance. Mass/volume conversion preserves original contribution units, overrides apply after aggregation, and stable item/contribution sorting makes regenerated results deterministic. Overrides may preserve a now-orphaned item, so removal is not simply “delete every item containing this recipe” ([groceries:237–267](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/lib/recipes/groceries.ts#L237-L267), [419–592](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/lib/recipes/groceries.ts#L419-L592)).

## Membership and shared-run lifecycle

Better Auth uses Mongo-backed email/password accounts; email verification is currently disabled, password reset delegates to mailer, and auth rate limiting is in memory ([auth:27–45](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/lib/auth/auth.ts#L27-L45)). Server authorization resolves current active membership and owner/editor roles. Lists embed memberships; they are not inferred from an account role, guessed list ID, or household label ([authorization:33–64](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/lib/auth/authorization.ts#L33-L64); [lists:196–255](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/lib/lists.ts#L196-L255)).

Purchased requests independently validate session, IDs, membership, active list/run, receipts, base revision, and current generated-item existence. Purchased and Already have are separate run state, not recipe edits or persistent inventory ([Purchased route:90–240](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/app/api/v1/lists/[listId]/grocery-items/[itemId]/purchased/route.ts#L90-L240); [architecture:95–111](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/docs/mvp/architecture.md#L95-L111)).

Completion creates minimal history and a fresh run in one Mongo transaction: delete the active run, insert history and replacement, update the list pointer and bounded completion receipts. History retains date/completer and pinned selections rather than the ingredient checklist. Realtime publication cannot undo the committed transaction ([completion:126–271](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/app/api/v1/lists/[listId]/complete/route.ts#L126-L271)). Review trigger: completion checks revision before entering the transaction, but its delete filter lacks that revision. Concurrent mutation/completion ordering merits a targeted review; static inspection does not prove a race-free snapshot.

## Offline, realtime, and worker boundaries

Dexie uses a per-user database with shell/run snapshots and operation records. Run snapshots contain selection summaries and grocery count, not a full persisted ingredient checklist. Queue metadata carries operation/client IDs, run ID, base revision, timestamps, attempts, and status ([database:5–73](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/lib/offline/database.ts#L5-L73); [mutations:9–36](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/lib/offline/mutations.ts#L9-L36)). Purchased and Already have buttons persist offline intent before changing local optimistic state ([Purchased button:34–55](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/components/lists/purchased-button.tsx#L34-L55)). This is narrower than universal offline editing.

Replay supports Purchased, Already have, amount overrides, and manual-item mutations. It coalesces latest intent per list/run/field/target while retaining unrelated fields, sends in deterministic timestamp/operation order, and retries a revision conflict once without the stale precondition. Thus conflict resolution deliberately favors latest queued field intent; it is not a general merge algorithm. Failed old-run operations receive an explicit completion explanation and never target the replacement run ([sync:36–160](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/lib/offline/sync.ts#L36-L160), [185–290](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/lib/offline/sync.ts#L185-L290)). Mount/online synchronization refreshes server state and displays failures; account cleanup deletes user Dexie data and private caches ([sync component:17–60](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/components/states/offline-mutation-sync.tsx#L17-L60); [database:210–252](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/lib/offline/database.ts#L210-L252)). Reloaded optimistic checklist reconstruction remains unproven by this review.

Socket.IO authenticates connections and reauthenticates list-room joins. Browser events are typed invalidation hints; duplicates are ignored, gaps trigger recovery refresh, and completion announces the fresh run ([realtime application:29–79](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/lib/realtime/application.ts#L29-L79); [run sync:148–196](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/components/states/realtime-run-sync.tsx#L148-L196)). Continuous room eviction after membership revocation was not established here.

The worker is a separate Agenda process with import retries. Contrary to architecture wording that the worker “receives only bounded fetch results,” its handler receives import identifiers, claims a user-scoped job, fetches the source itself, then passes bounded content to adapters. The adapter boundary, not the entire worker boundary, is where fetched-content-only isolation applies ([worker:10–38](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/server/worker/index.ts#L10-L38); [import handler:70–121](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/lib/recipe-import-worker.ts#L70-L121); [architecture:26–28,69–93](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/docs/mvp/architecture.md#L26-L93)).

## Work rules, verification, and reading map

Project decisions favor immutable provenance, conservative arithmetic, per-run pantry/order state, independently shared lists, and usefulness without a paid recipe provider. These are settled project rules, not evidence of Harry’s global preferences ([PRD:643–656](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/docs/mvp/prd.md#L643-L656)). Foundation ownership covers shared envelopes/configuration; feature work stays within assigned boundaries. The proposed `features/<slice>` layout is not the actual principal implementation layout, which uses `lib`, components, and routes ([ownership:680–718](https://github.com/harryt04/platter/blob/3368ef15ab2739e88ec0963d01bd6c58a3c4a2ec/docs/mvp/scaffolding-setup-instructions.md#L680-L718)).
