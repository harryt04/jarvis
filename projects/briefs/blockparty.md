## Purpose and actual state

Blockparty is a private browser property-trading game for 2–6 human/bot seats, with guest pseudonyms and invite admission. It aims for a complete classic-scale economic game in an original magical city. Accounts, matchmaking, spectators, chat, persistent profiles, and gameplay deadlines remain explicit non-goals. The implementation is substantial: lobby, deterministic rules, auctions/trades/debt, bot dispatch, MongoDB persistence, SSE recovery, completion/rematch, PWA shell, and consent-gated analytics exist. That is distinct from release readiness: CO-030 multiplayer/visual evidence and CO-031 accessibility remain partial; documentation closure, operational rehearsal, and final release approval are open. See [standing invariants](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/AGENTS.md#L48-L63) and [release queue](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/docs/delivery/classic-overhaul-backlog.md#L1083-L1277).

The **current code creates classic 1.0.0 games by default**. `DEFAULT_CONTENT_VERSION` selects `CLASSIC_BUNDLE`; server `CONTENT_VERSION` inherits it; creation loads that configured bundle. The registry retains the placeholder reader. Therefore AGENTS' opening claim that the runtime still defaults to placeholder, and classic.ts's introductory comment, are stale; README/docs index match source. This observation does not waive AGENTS' operating policies or imply production activation was independently verified. [Registry](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/packages/game-content/src/index.ts#L39-L72), [environment default](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/server/env.ts#L20-L49), [conflicting AGENTS text](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/AGENTS.md#L1-L21).

## Architecture and authoritative flows

There is one deployable Next.js App Router application. `apps/web/src/server` owns authentication, persistence, commands, projections, SSE, retention, and operations; client synchronization and components own presentation. `contracts` owns strict Zod wire schemas; `game-content` owns versioned data; `game-engine` owns pure resolution, legal actions, replay, invariants, and deterministic bot policy. Most rules live in a large `game-engine/src/index.ts`, so changes require following the relevant resolver and its `applyEvent` replay counterpart. ESLint prohibits browser imports of engine/database/server code and engine clock/IO/`Math.random`; `server-only` adds a framework boundary. [Enforcement](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/eslint.config.mjs#L73-L150).

**Create and admit.** The create UI starts with two Humans, zero Computers, Standard preset, and a chosen host piece. The strict request separately bounds human/computer counts to a combined 2–6 and requires matching preset/configuration. The route checks body size/media type, origin, CSRF, rate limits, and schema before opening a transaction. Creation captures content hash plus content/rules/variant/state/engine versions, creates a secret random 256-bit seed and lobby snapshot, and atomically inserts game, invitation, capability hashes, and audit record. Raw seat/host/reclaim credentials become cookies only after commit; the response supplies the invite path and lobby. [Contract](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/packages/contracts/src/api.ts#L27-L68), [route](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/app/api/games/route.ts#L34-L85), [creation](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/server/games/create-game.ts#L346-L448).

An invite reveals only admission facts and remaining pieces. Join verifies an unexpired lobby, unique active pseudonym, and an exact still-open piece. Its transaction updates seats and snapshot using the previous seats array as a predicate, then issues separate seat/reclaim hashes. A concurrent loser cannot displace the winning claimant. Invite possession never operates an occupied seat. [Admission implementation](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/server/games/join-game.ts#L146-L274).

**Start and act.** Lobby Start submits a normal versioned command; the server selects host authority from command type, rather than trusting a client host/actor flag. Within a Mongo transaction, receipt lookup precedes aggregate loading; a duplicate command ID returns its durable ACK without rerunning rules. New commands reject expired/terminal games, wrong capability kind, stale expected version, or unsupported captured rules. `capturedRuleSet` verifies bundle hash and schema consistency instead of consulting current deployment defaults. The engine separately validates phase, actor, funds, and rules. Start rejects open seats, records random seat order/deck shuffles, sets starting balances/inventory, and enters `AwaitRoll`. Roll records dice, movement, payments, and blocking continuations rather than asking the browser to calculate outcomes. [Route authorization](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/app/api/games/%5BgameId%5D/commands/route.ts#L41-L93), [captured rules](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/server/games/captured-rules.ts#L14-L39), [start resolver](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/packages/game-engine/src/index.ts#L2771-L2988), [roll resolver](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/packages/game-engine/src/index.ts#L5190-L5340).

Acceptance assigns one new aggregate version and contiguous journal sequences, asserts invariants, inserts events, conditionally replaces snapshot/version, and inserts the receipt before commit. Unique `(gameId, sequence)` and `(gameId, commandId)` indexes reinforce concurrency safety. Broadcast starts after the transaction returns. The browser uses a synchronous submission lock, preserves command identity after transport failure, and waits for an authoritative snapshot after ACK. An ACK is acceptance, not a speculative local state update. [Transaction path](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/server/commands/handle-command.ts#L563-L842), [indexes](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/server/db/collections.ts#L36-L68), [client submission](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/components/game/game-client.tsx#L335-L430).

**Reconnect and reconciliation.** Bootstrap supplies the seat projection, then named authenticated SSE events keep it current. MongoDB change-stream inserts reload the durable game and build an allowlisted projection per subscribed seat/capability kind; callbacks skip a version already superseded by a later transaction. Public journal redaction removes deck orders and other private replay facts. Recovery returns at most 256 contiguous events or a snapshot, with 100 recent public events for history. The browser does not run the reducer: event ranges advance delivery cursors, then `/sync` replaces state with the server projection. Decode failures, sequence gaps, transport loss, and visibility resume trigger recovery/backoff; ordinary ranges keep the socket open. [Fan-out](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/server/sse/change-stream.ts#L76-L160), [recovery](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/server/sync/recovery.ts#L128-L195), [client coordinator](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/client/sync/sync-client.ts#L125-L369).

## Recovery, bots, and sensitive boundaries

Presence is process-local, while pause/resume and host transfer become versioned journal transactions. A disconnected required human pauses play; host selection uses earliest connected tenure then stable seat order, revokes old host authority, and requires the selected seat to claim a distinct host cookie. Replacement/reclaim require an empty effect queue and no pending choice. Host replacement revokes the seat command capability while preserving reclaim authority; reclaim request identifies the returning seat from its claim, and host approval restores human ownership. [Presence recovery](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/server/recovery/presence-recovery.ts#L64-L365), [replacement/reclaim transaction](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/server/commands/handle-command.ts#L181-L397).

**Review trigger:** approval returns the target seat's new raw capability, and the commands route sets it on the *approving request's* response; approval simultaneously revokes the returning player's reclaim hash. No separate returning-device token exchange was found. This appears to hand the restored seat cookie to the host and needs a real two-device reclaim test before claiming the lifecycle works end to end. This is a source-derived concern, not an executed failure report. Relevant lines: [issuance/revocation](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/server/commands/handle-command.ts#L293-L338), [response cookie](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/app/api/games/%5BgameId%5D/commands/route.ts#L89-L93).

Bots choose from public state and legal actions, then use the same transactional handler with recorded rationale. The runner respects trade counterparties and auction priority, stops for humans/pause/finish, bounds work to 64 actions per slice, and continues bot-only games with event-loop yields. Human ACKs do not wait for bot completion; bootstrap/sync can restart work after process loss. [Runner](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/server/commands/run-bot-turn.ts#L35-L137).

Capabilities use random tokens, SHA-256 hashes at rest, production `__Host-` HttpOnly/Secure/SameSite cookies, and independent CSRF tokens. MongoDB must be a writable replica set; initial coordination/rate limiting assumes one web process. PWA caching covers public shell/assets, not game API state or offline commands. PostHog loads only after consent with capture/replay disabled except the explicit allowlisted transport. Gameplay extends game retention by 30 days; presence/recovery reads do not. [Authentication](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/server/auth/capabilities.ts#L19-L81), [PWA](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/app/sw.js/route.ts#L5-L99), [analytics](https://github.com/harryt04/blockparty/blob/09c695f3fa91617a2b13340a9e19c1d4e3e83cd2/apps/web/src/components/analytics/analytics-client.ts#L73-L139).
