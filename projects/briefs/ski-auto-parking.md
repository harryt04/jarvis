## Purpose and current state

A personal Next.js dashboard aims to monitor ski parking dates and optionally reserve spots. README describes Brighton automation, configurable intervals, logs, and educational use, explicitly warning that selectors need customization (`README.md:3–13,70–80,151–153`). Current types and UI extend dates to Brighton/Solitude, but the scheduler remains Brighton-only. Treat this as an unfinished browser-automation prototype, not demonstrated reservation infrastructure. There is no evidenced multi-user/account isolation, booking ledger, payment reconciliation, or durable worker recovery.

Architecture separates React controls, App Router HTTP handlers, synchronous filesystem storage, an in-process bot singleton, and two Puppeteer adapters. Dependencies pin Next 16.0.7 and React 19.2.0; Puppeteer and node-cron supply browser and schedule behavior (`package.json:14–27`). ## Settings → persistence → resort credentials

Dashboard loads config once, status/logs immediately, and status/logs every five seconds; unmount clears the timer. Settings POST serializes the entire local config. GET/POST config responses omit password; POST strips only `isRunning`, then shallow-merges everything else into existing configuration without runtime schema checks (`components/Dashboard.tsx:37–109`; `app/api/config/route.ts:4–28`). Dates, intervals, credential types, arbitrary extra keys, and auto-book values therefore depend on caller trust rather than server validation.

Storage creates `data` relative to process working directory at module load; `config.json` is read/parsed and synchronously overwritten. Errors reading fall back to defaults; writes are neither atomic nor locked. Password hashing/verification helpers exist but are unused by this persistence path: password reaches JSON unchanged and is later passed to the resort login (`lib/config/storage.ts:6–60`; `lib/bot/manager.ts:115–118`). README's encrypted-storage feature conflicts with both implementation and its later “not hashed” note (`README.md:11,109–113`). Hashing alone would not supply a recoverable password for external login.

A consequential UI bug follows password omission: load/save response resets local password to empty, and a subsequent full save can overwrite the stored password with that empty value. “Test Connection” uses saved server settings, not unsaved form input; README orders testing before saving (`components/Dashboard.tsx:51–61,87–117`; `README.md:40–44`). There is one shared username/password pair for both resort adapters.

## Start → scheduler → booking reconciliation

Start validates only credential truthiness, nonempty targets, and current in-memory running status. It marks memory/disk running, creates `*/N * * * *`, and awaits an immediate check before returning. Cron is minute-field stepping, not a guaranteed elapsed-N-minute timer. Status predicts the next run with elapsed minutes, potentially disagreeing with cron. Schedule creation failure occurs after the running flag changes (`lib/bot/manager.ts:20–60,92–101`).

The major migration seam: `TargetDate` is `{date,resort}`, yet manager passes each whole object to scraper methods accepting strings, interpolates objects into logs, and always initializes Brighton. This is a static type mismatch and wrong routing, not proven functioning dual-resort automation (`lib/types.ts:3–15`; `lib/bot/manager.ts:105–159`; `lib/bot/brighton-scraper.ts:114–117,199–202`).

Each cycle rereads config but keeps the original cron schedule and logged-in browser. No overlap guard protects the shared page from concurrent cycles; settings changes do not force reauthentication. Success removes a target by object identity from the cycle's snapshot. Multiple successes can rewrite targets from that same stale snapshot, reintroducing previously removed entries; concurrent saves can also be overwritten (`lib/bot/manager.ts:92–173`). Stop stops scheduling and closes the browser, without an explicit cancellation/join protocol for an active cycle. Errors reset the browser; login failure calls stop. Counters live only in process memory, while persisted `isRunning` has no startup restoration path (`lib/bot/manager.ts:9–18,63–89,198–215,251–252`).

## Availability and selectors: implemented versus intended

Calendar checks are manual, store results in component memory, and can request both resorts concurrently. Each HTTP request launches its own browser, logs in with persisted credentials, checks dates sequentially, then closes. Validation checks only a nonempty array and resort enum; no date-element validation or request cap exists. Exceptions lack `finally` cleanup (`components/AvailabilityCalendar.tsx:26–88`; `app/api/availability/route.ts:7–66`). This is separate from scheduler status and logs.

Both adapters launch headless Chromium with sandbox disabled, use broad login button text and generic email/text/password selectors, then infer authentication from page text containing “reserve” (Brighton also “parking code”). Those words do not establish an authenticated identity (`lib/bot/brighton-scraper.ts:10–107`; `lib/bot/solitude-scraper.ts:10–107`). Brighton defaults to the parking-code/free route; paid mode exists as a method argument but is not exposed by manager/API. Solitude searches “reserve a parking spot.”

Actual calendar selectors remain `[data-date], .calendar-day, .date-cell`; absent a matching date, any “select” or “available” text yields availability. Broad sold-out text anywhere yields false; caught errors also become false, which UI labels “Full.” Booking repeats availability navigation, clicks a broadly matched date and confirmation button, then reports success because a click occurred—not because a reservation ID or server confirmation was reconciled (`lib/bot/brighton-scraper.ts:120–195,205–275`; `lib/bot/solitude-scraper.ts:117–185,189–262`; `components/AvailabilityCalendar.tsx:141–169`). README's placeholder warning remains materially accurate. CUSTOMIZATION examples, including `:contains`, are suggestions, not the selectors executed in adapters (`CUSTOMIZATION.md:21–74`).
