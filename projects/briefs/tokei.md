## Purpose and current structure

README and `app/layout.tsx:22–32` position Tokei as a free kitchen timer for power users coordinating dishes. Working source implements authenticated freestyle timers and Mongo-backed routine definitions: parallel swimlanes, ordered steps, automatic/manual starts, preparation tasks, and recipe notes (`models/routine.ts:5–48`). It is a Next.js 16 App Router application with React hooks, Tailwind/shadcn components, Better Auth, MongoDB, and PostHog. It does not establish an OS alarm service, durable execution history, or cross-device live execution. Synchronization groups exist as types, but the runner does not consume `syncConfig`; their presence is not proof of group scheduling.

## Flow 1: identity → saved definitions → ownership

Sign-up calls Better Auth email registration or Google social sign-in and returns to `/freestyle` (`app/sign-up/page.tsx:28–52`). `lib/auth.ts:6–20` connects at module initialization, uses the Mongo adapter with transactions disabled, enables email/password and Google, and installs `nextCookies`. Mongo access is a module singleton; database selection is `tokei-${NODE_ENV}` (`lib/mongo-client.ts:12–31`). Auth storage is delegated to Better Auth; routines are the explicit application collection.

`proxy.ts:4–16` checks cookie presence for protected path prefixes. This is a navigation gate, not session validation. Server pages and APIs call `auth.api.getSession`. The routines page filters by session user, serializes `_id`, and passes initial data into `RoutinesList` (`app/routines/page.tsx:9–33`). `useRoutines` fetches only when initial data is empty; mutations await API responses before reconciling its array (`hooks/use-routines.ts:15–76`). `lib/api.ts:16–65` uses POST for both create and update and unwraps `updatedRoutine`. Name edits debounce two seconds or save on blur; child edits reconcile into `currentRoutine`, and tab changes ask dirty child editors to save (`view-routine.tsx:60–109`, under `components/custom/`). This is definition persistence, not execution persistence.

Two consequential ownership defects are visible. List API filtering and single GET/DELETE checks are present (`app/api/routines/route.ts:21–24`; `app/api/routine/route.ts:28–36,131–142`). But POST looks up and updates solely by `_id`, then stamps the caller's user ID, allowing an authenticated caller with another routine ID to overwrite and take ownership (`app/api/routine/route.ts:65–99`). The detail server page also reads solely by `_id` and renders without comparing ownership (`app/routine/[id]/page.tsx:25–37`). This exposes another user's definition through the page even though API GET checks ownership. A unit test explicitly records the update defect (`__tests__/api/routes.test.ts:523–545`); passing that test would preserve it.

POST spreads arbitrary JSON without a server domain schema; missing update targets insert, invalid ObjectIds fall into generic 500 handling. Routine form submission simply casts the state and closes (`components/custom/routine-form.tsx:45–51`). Do not infer runtime validation from TypeScript types or installed Zod. The Mongo connection module contains a credential-bearing fallback literal (`lib/mongo-client.ts:2–6`), intentionally not reproduced here; absence of the environment override therefore does not reliably fail closed. No credential validity was checked.

## Flow 2: routine definition → schedule → ticks and alerts

`components/custom/view-routine.tsx:123–134` translates “now” into a computed completion date or “timed” into a local time-of-day date, then mounts the runner. The start dialog interprets elapsed clock times as tomorrow and validates available duration with a 60-second allowance (`start-routine-dialog.tsx:66–97`), but `lib/utils.ts:26–35`, used by the parent, always constructs **today**. Overnight validation and actual execution therefore disagree.

`hooks/use-routine-timer.ts:175–223` sums each lane's steps, then delays shorter lanes to align with the longest duration or target end. Steps follow array order; `sequence` is not the scheduling mechanism. Waiting ticks subtract one second every 1,000 ms (`:255–280`); active steps increment percentage every 100 ms (`:336–369`). Neither reconciles progress against actual elapsed wall time. Completion advances the lane, starts automatic successors after 300 ms, or requests a manual start; finishing all lanes sets stopped (`:378–459`). Recalculation only shortens waits, aligns remaining step durations, and can force a manual first step to start (`:468–567`). Thus a requested finish time is an initial coordination input, not a hard deadline.

Preparation checkboxes produce a blocked-lane set in `components/custom/run-routine-component.tsx:31–73`. Blocking is checked in `onWaitComplete`, but immediate starts in `startAllTimers` bypass it (`hooks/use-routine-timer.ts:228–247,286–329`): a zero-wait lane can start before prep. Pauses clear intervals; unmount does likewise. The delayed successor timeout is not tracked for cancellation, creating a stop/unmount lifecycle concern. Routine execution and completed prep IDs live in React state; reload discards them. “Start Over” explicitly reloads (`run-routine-component.tsx:87–94`).

Routine transitions call `toast`, not sound or browser Notification APIs. No mounted `Toaster` usage was found, although its component exists; visible delivery is therefore unverified. `speakText` exists but has no discovered caller (`lib/utils.ts:38–50`). These paths provide no evidenced browser/OS background guarantee: suspended callbacks cannot maintain tick accuracy, and closing the page removes execution. No service-worker scheduler or push path was found.

## Flow 3: freestyle → local backup → alarm

`components/custom/freestyle-list.tsx:21–52` restores and backs up `freestyleTimers` in localStorage, with no user namespace, date revival, or parse-error guard. Clearing all timers explicitly writes an empty array. Names, durations, and timestamps survive locally; running state does not. The timer initializes stopped on every mount (`freestyle-component.tsx:31–45`). Starting records `startedAt`/`willEndAt`, drives a timestamp-based Countdown display, and independently advances progress through recursive timeouts (`:50–103,149–154`). Completion sound follows that progress loop, so display and alarm can diverge under throttling. Howler plays a single relative `default-alarm.wav`; stopping the alarm calls `stop` (`lib/utils.ts:45–50`; component `:70–79`). There is no completion notification request or OS scheduling contract. Audio audibility, autoplay policy, suspension, and device mute were not exercised.

## Integrations, verification, and decisions

Authenticated routines list/detail renders invoke `addUser`, posting email plus `usesApps: ['tokei']` to the shared portfolio CRM; it swallows rejected fetches and does not inspect HTTP status (`lib/utils.ts:117–129`). This is repeated render-time registration, not demonstrated deduplication or consent logic. No request was sent.

Themes use next-themes, system default, and light/dark/automatic options (`app/layout.tsx:50–55`; `providers/themeProvider.tsx:7–18`; `components/custom/theme-switcher.tsx:27–35`). PostHog initializes only in production browsers and captures pathname pageviews through `/ingest`, but its public key check runs even in development (`providers/posthogProvider.tsx:8–35`). `next.config.js:7–29` proxies ingestion; server analytics factory exists without a discovered application caller.

`package.json:5–20` declares Node 24, dev/build/start, `next lint`, Jest, Playwright, formatting, and index creation. Jest uses ts-jest/node and `__tests__/**/*.test.ts` (`jest.config.ts:3–28`): inspected coverage includes mocked API/auth/Mongo, fetch wrappers, utilities, proxy, and analytics—not hook execution or real database integration. Playwright uses Chromium, external `BASE_URL` or localhost:3000, CI retries/workers, and a **commented-out** webServer (`playwright.config.ts:3–34`). E2E files cover landing/auth UI, redirects, and 404s; an invalid-cookie test accepts either freestyle or sign-in, weakening its assertion. No `.github` directory or explicit deployment pipeline was found. AGENTS claims builds skip ESLint, but current Next config contains no such setting; the declared `next lint` command needs compatibility verification. Index creation touches both development and production databases (`gulpfile.ts:4–6`), not just the current environment.

Project-scoped guidance: AGENTS explicitly favors hooks/ref synchronization, Mongo singleton/config, plain domain types, and preserving UI primitives. Kitchen alignment is documented product intent; dependable background delivery is not an established decision. No broader Harry preference is inferred.
